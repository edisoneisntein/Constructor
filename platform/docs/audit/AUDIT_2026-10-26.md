# Auditoría Técnica, Refactorización y Optimización — Constructor REA (SIREP)

**Fecha:** 2026-10-26 · **Alcance:** `platform/backend` (FastAPI + SQLite/PostgreSQL), `platform/frontend` (Next.js 15 + TS + Tailwind)
**Método:** evidencia por Constructor REA/SIREP (motor propio, `deep_analysis=true`) + criterio por Remix VIP (`auditor_elite`) + auditoría estática manual reproducible.

## 1. Executive Summary

**Salud técnica:** plataforma con arquitectura por capas coherente (`api → services → repositories/engines → core`), sin ciclos de importación y con una suite de 22 archivos de prueba en verde (**176 pruebas, 6 saltadas**). El riesgo no está en el diseño base, sino en **acumulación de deuda dentro de módulos grandes** y en **límites de confianza que no se aplican donde toca**.

## 3. Optimization Dossier

### 3.1 Performance

- **Memoria acotada en análisis binario (aplicado).** `extract_strings` es el punto de entrada más hostil del sistema: un binario de 64 MiB con bytes imprimibles alternos generaba millones de objetos `str`. El nuevo recorrido conserva solo las primeras 200 cadenas únicas y, dentro de cada corrida, los primeros `max_length` bytes; añade salida temprana cuando se alcanza el tope ASCII.
- **Transferencia BD→Python (aplicado).** El resumen de análisis pasó de cargar el grafo completo (`nodes`, `edges`, `dependencies`) a tres agregados `COUNT(*)`. El export deja de materializar el grafo dos veces.
- **Complejidad lineal en el escaneo de modelos (aplicado).** El número de línea se acumula incrementalmente en lugar de recountar el prefijo completo por coincidencia.
- **I/O redundante (pendiente).** Los archivos JS/TS se leen dos veces (bridge Node + orquestador Python). Solución de bajo riesgo: devolver las referencias a modelos detectadas desde el bridge y eliminar la segunda lectura.
- **Trabajo no acotado por tamaño de entrada (pendiente).** ELF: hasta 4096 cabeceras × 1 MiB de copia+entropía (`binary_analysis/elf.py:88-99`); el presupuesto real puede superar 4 GiB de escaneo para una entrada de 64 MiB. Requiere un presupuesto agregado de bytes.
- **Captura de salida de subproceso sin cota (pendiente).** `validation/engine.py:326` acumula stdout+stderr completos antes de recortar a 4.000 caracteres; el recorte es de presentación, no de recurso. Redirección a fichero temporal con lectura de cabeza/cola.
- **Transacciones de progreso (pendiente).** Un `COMMIT` por archivo analizado puede llegar a ~20.000 commits por análisis. Agrupar por lote o por tiempo, separando la cadencia del latido.

### 3.2 Readability / Maintainability

- **Duplicación eliminada:** `is_cancel_requested` (dos definiciones), compilación de regex por llamada (`gemini_detector`, `binary_analysis/utils`), parseo JUnit duplicado, cabeceras de auth duplicadas en el cliente HTTP del frontend (`lib/api.ts` ahora usa `authHeaders()` + `request()` comunes).
- **God objects pendientes de división (por este orden):**
  1. `db/repositories.py` → `users_sessions`, `projects_artifacts`, `jobs_findings`, `graph`, `changes_migrations`, `validation` (mantener `repositories.py` como fachada re-exportando, sin romper imports).
  2. `engines/analysis/source_analysis.py` → `phases/` (manifest, AST, REA, summary) + emisores por regla en `_emit_file`.
  3. `schemas/models.py` → un módulo por contexto, preservando `schemas/__init__.py`.
  4. `engines/validation/engine.py` → estrategia por tipo de check + parser JUnit aislado.
  5. `db/database.py` → DDL y migraciones en módulos propios; una única definición del DDL del grafo.
- **Transacciones:** definir una única autoridad (middleware) y eliminar los `commit()` dispersos en servicios, o centralizarlos en un Unit of Work explícito.
- **Front:** cuatro rutas y ocho componentes son `"use client"` sin store compartido; el estado de carga inicial falta en `app/projects/[id]/page.tsx:75` y en `MigrationPanel`, `BinaryAnalysisPanel`, `ChangeSetPanel`, `ValidationPanel`. Extraer un hook `useApiResource` resolvería carga/error/refresco sin introducir una librería.

### 3.3 Scalability

- **Cola de trabajos:** `claim_next_job` es atómico en SQLite por el escritor serializado, pero **no** es seguro con varios workers en PostgreSQL: falta `FOR UPDATE SKIP LOCKED` (`db/repositories.py:519-527`). Aplicado en esta iteración: el guard de propiedad (`claimed_by`) en `update_job` y `heartbeat_job` ya impide que un worker perdedor corrompa el estado.
- **Reanudación:** `claim_next_job` no filtra por `attempt_count`, por lo que un job `QUEUED` agotado puede volver a ser reclamado; `worker_claim_batch` está definido y no se usa (`core/config.py:144`, `app/worker.py:87`).
- **Perfil de riesgo:** el worker externo siempre ejecuta `deep_analysis=False` porque la columna no existe en `analysis_jobs` (`app/worker.py:106`, `db/database.py:90`): la opción del usuario se pierde al encolar.
- **Aislamiento multi-tenant:** las tablas de validación no tienen `organization_id` (`db/database.py:335-365`); el validator opera sobre el root del backend y registra auditoría con `organization_id=None` (`services/validation_service.py:183`).
- **Límite de concurrencia:** el pool inline usa 4 hilos para trabajo CPU-intensivo en Python (GIL): no hay paralelismo real en la fase AST (`services/job_runner.py:24-32`). Para cargas mayores, migrar a procesos o a workers externos.

```typescript
// DESPUÉS
export const API_BASE = (
  process.env.NEXT_PUBLIC_API_BASE ?? "http://127.0.0.1:8000"
).replace(/\/+$/, "");
const REQUEST_TIMEOUT_MS = 30000;

async function request(path: string, init: RequestInit): Promise<Response> {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), REQUEST_TIMEOUT_MS);
  try {
    return await fetch(`${API_BASE}${path}`, {
      ...init,
      headers: authHeaders(init),
      signal: init.signal ?? controller.signal,
    });
  } finally {
    clearTimeout(timer);
  }
}
```
**Justificación técnica:** (a) el fallback `8001` no correspondía con el puerto real del backend (`8000` en `README.md:38` y `Dockerfile:25`), por lo que el frontend fallaba sin `NEXT_PUBLIC_API_BASE`; (b) sin `AbortController` una petición colgada bloquea la UI indefinidamente; (c) `JSON.parse` antes de comprobar `response.ok` convertía un error HTML del proxy en `SyntaxError` en lugar de `ApiError`; (d) `api()` y `downloadExport()` compartían cabeceras duplicadas → un único `authHeaders()`.
